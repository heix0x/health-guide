# 一个应用，两个地址

线上只有一条链接。根上是一张书目索引，两本书各占一个子路径：

```
/                    索引（选哪本）
/student-health/     高中生身体健康指北
/smoke/              一根烟的事
```

分享时给的是子路径，不是索引。读者拿到 `/smoke/` 就直接进烟那本，不会先看到一张「这里还有本给高中生的」的封面。

**为什么不是两个应用**

本来就是这么打算的：`student-health/` 一个应用、`smoke/` 一个应用，两条链接互不相干。试了，做不成——发布工具按工作区根目录里的 `.wbapp_*.genie` 标记认应用，**一个工作区只对应一个应用**。分别以两个子目录发布，两次都落到同一个应用、同一条链接：第二次直接覆盖第一次。线上先是一分钟的学生册，然后变成了烟。

所以「两个独立应用」在现有工具下要么做不到，要么得把一本书搬出仓库——那会把路径、文档分层、共用约定一起拆散，代价远大于收益。

**为什么不是一条链接只放一本**

另一本就只剩 PDF 能传播，线上等于不存在。两本书都要能发链接，这是这条决策的起点。

**索引页为什么要一段脚本**

线上地址必须带 `?sharecode=`，不带就是「链接不完整」。索引页里的相对链接会把 query 丢掉，所以页尾有一小段脚本，在加载时把当前的 `location.search` 接到两个入口上。

没有把 sharecode 写进源码：它属于某一次部署实例，写死之后换一次发布、或者把仓库发给别人，源码就带着一个失效参数。索引页保持与实例无关。

**考虑过的方案**

- 两个独立应用：工具不支持，见上。
- 索引页硬编码 sharecode：源码被绑死在当前实例上。否决。
- 把仓库根目录直接发布（根目录放一张 `index.html`）：会把 `*/docs/资料库/` 一起上传——那里有真实姓名和 QQ 号。否决，改成先构建 `public/`。
- 不做索引，只用两条 `?sharecode=` 长链接：少一个页面，但一旦要加第三本书，就得再复制一遍长链接，没有任何地方能列全。

**代价**

- 线上地址与目录结构不再是一比一：`public/` 是产物，改了源必须重跑 `tools/assemble_public.py` 再发布，否则线上还是旧的。这和 PDF 那条规律是同一条（AGENTS.md 第 12 条）。
- 索引页多一个 4 KB 的脚本。关掉 JS 的读者点进去会看到「链接不完整」——把手上的完整链接直接给他仍然能用。
- 两本书共用一个应用：一个域名、一份配额、一次发布。任一本发布失败，两本一起不可用。
- 线上没有 PDF 下载入口。要纸质版的人走「打印全册」，或者找本地要文件。
